# dapr4s

| CI | Release |
| --- | --- |
| [![Build Status][Badge-GitHubActions]][Link-GitHubActions] | [![Release Artifacts][Badge-MavenCentral]][Link-MavenCentral] |

A Scala 3 library that exposes every [Dapr](https://dapr.io) building block as a
**capture-checked capability**. Dapr effects — state, pub/sub, service invocation,
secrets, configuration, bindings, distributed locks, actors, workflows,
cryptography, jobs, and conversation (LLM) — are
modelled as `scala.caps.Capability` values that the compiler tracks. User code
compiles under `import language.experimental.safe`, so the compiler statically
guarantees that a Dapr resource can never escape the scope that owns it. The Dapr
SDKs (Java SDK on the JVM, `@dapr/dapr` on Scala.js) are hidden entirely; users
see only Scala types.

## Requirements

- Scala `3.10.0-RC1-…-NIGHTLY` (capture checking / safe mode; exact version pinned in `buildsupport.mill`)
- Nothing else for the build: [Mill](https://mill-build.org/) 1.3.1 runs from the `./mill` bootstrap script and
  downloads the JDK it needs (Zulu 25)
- For Scala.js builds: npm (the build installs `package-lock.json` itself); Node 25+ to run
  capability-touching code (the Wasm + JSPI integration tests)
- Docker (only for the integration tests, which exercise a real `daprd` sidecar + Redis)

## Build & test

Sources live in `src/{shared,jvm,js,wasm}` and `test/{shared,jvm,js,wasm}`. The Mill modules are
`core.jvm` / `core.js` (the library; `core.<p>.test` are its unit tests), `integration.jvm` /
`integration.js` (the Docker integration suites under `test/*/integration`), `stFacades` (the
ScalablyTyped facades of `@dapr/dapr`, express and Node, generated by the build) and `wasm.*` (the
WASI-component platform, see AGENTS.md).

```bash
./mill core.jvm.compile              # JVM
./mill core.jvm.test                 # JVM unit tests
./mill integration.jvm.testForked    # JVM integration tests (needs Docker)

./mill core.js.compile               # Scala.js (first run generates + compiles the facades, ~10 min)
./mill core.js.test                  # Scala.js unit tests (plain JS backend)
./mill integration.js.testForked     # Scala.js integration tests (Docker + Node 25 on PATH; Wasm + JSPI)

./mill mill.scalalib.scalafmt.ScalafmtModule/scalafmt   # format (add --check to only check)
```

The JS integration suites are a separate project because they use orphan `js.await`, which
needs the WebAssembly backend with JSPI (and wedges the plain-JS linker); `integrationJS` links
them for Wasm and runs them against a real `daprd` 1.17 + Redis environment.

## Usage

```scala
//> using dep "com.github.sideeffffect::dapr4s::<version>"
```

(The `::` before the version resolves the right platform artifact — `dapr4s_3` on
the JVM, `dapr4s_sjs1_3` on Scala.js.)

```scala
import dapr4s.*
import dapr4s.state.*   // each capability family has its own package: dapr4s.state, dapr4s.invoke, ...

// Asks only for read-only access to one store: it cannot save, delete or run a transaction.
def lookup(key: StateStoreKey)(using StateCapability.Instance.ReadOnly): Option[String] =
  StateCapability.Instance.ReadOnly.get[String](key)

def remember(key: StateStoreKey, value: String)(using DaprCapability): Option[String] =
  DaprCapability.state(StateStoreName("statestore")):   // StateCapability.Instance in scope
    StateCapability.Instance.save(key, value)
    lookup(key)                                         // the full Instance also satisfies ReadOnly
// Using the StateCapability.Instance outside the block is a compile error.
```

`DaprCapability` has one member per building block (`state`, `publish`, `invoke`, `secrets`,
`configuration`, `bindings`, `lock`, `actor`, `workflow`, `crypto`; on the JVM also `jobs` and
`conversation`). Each returns the family's **universal** capability, which reaches any store /
component / app and takes the name on every call. `instance(name)` narrows it to an `Instance`
bound to one name. State, Secrets, Configuration, Jobs and Workflow also have read-only tiers
(`X.ReadOnly`, `X.Instance.ReadOnly`): upcast to narrow the authority — narrowing a read-only
capability by name keeps it read-only. Actors have two levels: `forType(actorType)`, then `instance(actorId)`.

```scala
import dapr4s.*, dapr4s.state.*, dapr4s.invoke.*, dapr4s.actor.*, dapr4s.workflow.*

def tour()(using dapr: DaprCapability): Unit =
  val store = StateStoreName("statestore")
  dapr.state.save(store, StateStoreKey("k"), "v")                         // StateCapability (universal)
  dapr.state.instance(store).save(StateStoreKey("k"), "v")                // StateCapability.Instance
  dapr.invoke.invoke[String](AppId("orders"), InvokeMethodName("ping"))   // InvokeCapability: appId per call
  dapr.actor.forType(ActorType("Counter")).instance(ActorId("c-1")).invokeVoid(ActorMethodName("reset"))
  val id = dapr.workflow.start(WorkflowName("OrderWorkflow"))             // WorkflowCapability
  dapr.workflow.instance(id).suspend()                                    // WorkflowCapability.Instance
```

Every capability interface's companion object forwards its methods from a `using` capability
(`StateCapability.Instance.save(key, value)`, `WorkflowCapability.start(name)`, ...), and has
`instance(name)` accessors that narrow the capability in scope and return it
(`StateCapability.ReadOnly.instance(name)` returns a `StateCapability.Instance.ReadOnly`).

## Errors

Expected outcomes are values (`None` for a missing key, `Option[ETagMismatchException]`, `UnlockStatus`,
`BulkPublishResult`). Sidecar errors are thrown as one sealed `dapr4s.DaprException` hierarchy, the same on
the JVM and on Scala.js — no Dapr SDK exception type reaches your code:

```scala
try dapr.state.get[String](StateStoreName("orders"), StateStoreKey("k"))
catch
  case e: ComponentNotFoundException => ???   // e.componentKind == DaprComponentKind.State, e.name == "orders"
  case e: PermissionDeniedException  => ???   // access policy / scope
  case e: AppUnreachableException    => ???   // invoke: unknown or unhealthy app (e.appId)
  case e: InvokeHttpException        => ???   // invoke: the app answered non-2xx (e.status, e.body)
  case e: DaprApiException           => ???   // anything else (e.errorCode)
```

For HTTP-level service invocation that returns every answer as a value, use
`invokeHttp(appId, method, body, httpMethod, headers, query): InvokeResponse(status, headers, body)`.

## Platforms

The public API is identical on the JVM and on Scala.js — synchronous, direct style
on both. On the JVM, blocking calls park virtual threads; on Scala.js, the same
calls suspend the WebAssembly stack via JSPI (JavaScript Promise Integration)
while the Node event loop keeps running.

**Scala.js supports the full capability matrix** — state, pub/sub, invocation,
bindings, secrets, configuration, locks, crypto, actors, workflows, and
`serve()` with full app-channel parity (subscriptions, invoke routes, input
bindings, job routes, actor hosting, workflow hosting) — **except `jobs` and
`conversation`**, which the Dapr JS SDK has no API for. On Scala.js those two
methods simply don't exist at compile time (they live on a JVM-only platform
trait), so using them is a compile error, not a runtime exception — use the JVM
platform for those.

JS consumers of capabilities must link with the experimental WebAssembly backend
and run on Node 25+ (or Node 23/24 with `--experimental-wasm-jspi`); the pure
parts of dapr4s (models, codecs, derivation) also link on the plain JS backend:

```scala
//> using platform "scala-js"
//> using jsEmitWasm true
//> using jsModuleKind "es"
//> using jsEsVersionStr "es2017"
//> using dep "com.github.sideeffffect::dapr4s::<version>"
```

Run `npm install @dapr/dapr` so the SDK is resolvable from the directory Node
executes in, then enter `js.async { ... }` once at the program edge (or use the
JS-only `runAsync`/`serveAsync`, which wrap it for you):

```scala
import dapr4s.*
import dapr4s.state.*
import scala.scalajs.js

// one-shot request/response, with the single js.async entry at the program edge:
def main(args: Array[String]): Unit =
  js.async {
    Dapr().run:
      summon[DaprCapability].state.instance(StateStoreName("statestore")).get[String](StateStoreKey("k"))
  }: Unit
```

### Scala.js facades: embedded — consumers need only Maven Central

The `dapr4s_sjs1_3` artifact is **self-contained**: the ScalablyTyped-generated facades of
`@dapr/dapr`/express/Node that the JS interop layer is written against ship **inside the
dapr4s jar** (under the dapr4s-specific `dapr4styped.*` package, so they can never collide
with a `typings.*` generation of your own), and the POM references only Maven-Central
artifacts. Using dapr4s from Scala.js is therefore an ordinary dependency — no converter, no
local ivy repository, nothing beyond the `using dep` above plus `npm install @dapr/dapr`.

**Building dapr4s itself** (this repository) generates the facades in the build: the
`stFacades` module runs the ScalablyTyped converter over the repo's `node_modules`
(installed from `package-lock.json`) and compiles the result. `./mill core.js.publishLocal` packs
their `.sjsir` into the jar; nothing needs to be generated by hand.

### WASI components (prototype)

A dapr4s app can also be built as a WASI component for
[dapr-wasm-components](https://github.com/sideeffffect/dapr-wasm-components) (the scala-wasm fork of Scala.js).
A build plugin carries all the build logic, for Mill (`mill-dapr4s-wasm`) and for sbt (`sbt-dapr4s-wasm`).
With Mill:

```scala
//| mvnDeps: ["com.github.sideeffffect::mill-dapr4s-wasm::<version>"]
package build
import mill.*, mill.scalalib.*
import dapr4s.millwasm.*

// + app/wit/world.wit (`include dapr-wasm-components:interfaces/app@0.7.5;`), app/wkg-config.toml, app/wkg.lock
object app extends Dapr4sWasmComponentModule {
  def scalaVersion = "<the Scala 3 nightly dapr4s is built with>"
  def mvnDeps = Seq(mvn"com.github.sideeffffect::dapr4s-wasm::$dapr4sWasmVersion")
}
// + in the app's sources: object dapr4s.wasm.ComponentRoot { def component: DaprComponent = MyComponent }
```

`./mill show app.dapr4sComponent` builds the component and prints its path. The tools on the PATH: `wkg`,
`wasm-tools` (and `wit-bindgen-scala` only for a `WitBindgenModule`). See AGENTS.md "Wasm component layer
rules" and [dapr4s-examples](https://github.com/sideeffffect/dapr4s-examples) (examples 18 and 19).

See [`DESIGN.md`](docs/DESIGN.md) for the architecture, the two-layer
(safe / `@assumeSafe` shell) model, and the Scala.js platform details, and
[dapr4s-examples](https://github.com/sideeffffect/dapr4s-examples) for runnable examples.
